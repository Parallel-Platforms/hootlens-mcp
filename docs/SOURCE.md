# Source provenance

This checkout prepares `@hootlens/mcp` 1.1.0 from the reviewed monorepo commit `683b3ac9294e9db795607470dc632c13f79d68b8`. It is not the source identity of the already published 1.0.2 package. [SOURCE.json](SOURCE.json) records the imported commit, proposed release tag and SHA-256 hashes of the complete MCP and shared core source, registry manifest, license and changelog. Hashes normalize CRLF to LF so Windows and Linux verify the same text.

The original server and shared core import comes from that exact commit. Immutable monorepo commit `cb4bbddb432716d02a0cfb4224823810f0fb8c3e` supplied the explanation side-effect and minimized duplicate-input contracts. The latest update imports `src/apps.generated.ts`, `src/apps.ts`, `src/docs.generated.ts` and `src/tools.ts` from immutable monorepo commit `3ab8815c4d695947a116d227cd487142e2efc604`. `SOURCE.json.sourceUpdates` retains the earlier updates and records this superseding per-file identity; the current normalized bytes of these four files match the latest commit.

The widget update declares the existing dedicated Hoot Lens origin, `https://mcp.hootlens.com`, in `ui.domain` and offers an explicit bounded "Load click density" action when the initial result omitted grid cells. `maxCells: 0` still returns only the requested summaries and no density. The action requests at most 200 cells for the same project and cohort through the existing authorized host, with loading, refusal/retry and stale-response handling. It does not expand the initial result or its hidden metadata, change scopes, relax the asset/frame CSP, create DNS or claim a separately deployed UI site. Earlier semantic safeguards remain: explanation generation has non-destructive side effects and no guarantee of idempotent retries; duplicate checks exclude unused report body, kind and tracker version. All other runtime source stays unchanged. Shared core source and generated MCP resources are included so no private repository access is required to build. No API implementation, server credentials, environment file or customer data is exported. The public build script adapts the two-bundle builder to this repository. The root manifest stays `private: true`; dependencies, source inventory and compiled version are checked before staging the strict npm payload.

Version 1.1.0 has not been published by this preparation. Its snapshot deliberately has no `npmIntegrity`, npm `gitHead` or claimed attestation. The imported monorepo commit and a future public release commit are different identities. Source hashes and successful fixture tests are not npm provenance or a binary reproducibility claim. Historical published 1.0.2 source and security evidence remain available in Git history and the versioned security evidence documents.

## Synchronize an already published source snapshot

These steps describe historical exports from the monorepo's existing publisher. Preparing a new unpublished release through public CI uses [RELEASING.md](RELEASING.md) instead. For that migration, the new npm `gitHead` and attestation identify the public build commit; the imported monorepo commit remains a separate source reference. Do not claim the two commit identities or independently built bundle bytes are identical.

1. Fetch the exact release tag from the owner's monorepo. Compare its commit with `npm view @hootlens/mcp@VERSION gitHead dist.integrity --json`. Do not export a development branch under a published version.
2. Copy `services/mcp/src`, the shared `packages/core` source required by it, `server.json`, `LICENSE` and `CHANGELOG.md`. Review the complete file set for secrets and customer data. Preserve the source mirror's build, test and CI files.
3. Update the root manifest and dependency lock from that release, keeping this mirror private. Adapt build paths and include any new shared runtime dependencies. Regenerate the normalized hashes and release identity in `SOURCE.json` from the tagged source, rather than hashing an unverified working tree.
4. Run `npm ci`, `npm run typecheck`, `npm run build`, `npm test`, and check the built executable's version. Review the actual public CI matrix, the installed npm artifact and the hosted endpoint separately.
5. Open a public repository PR. Merge after independent review and passing required checks. Synchronize official registry metadata with the already published npm version, using the owner's existing domain proof. Historical exports do not authorize republishing an existing npm version. A future migration to public CI requires the separate [release preparation and owner setup](RELEASING.md); its proposed pipeline remains unpublished until those conditions are met.

Neither a local fixture test nor a matching version proves production authorization, customer capture, signed-in client compatibility or directory acceptance. Keep those checks in their own evidence records.
