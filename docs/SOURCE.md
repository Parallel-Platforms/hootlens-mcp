# Source provenance

Published `@hootlens/mcp` 1.1.0 was built from public commit [`f06d28882ce38f9bce4d4b55d31c61189cc92415`](https://github.com/Parallel-Platforms/hootlens-mcp/commit/f06d28882ce38f9bce4d4b55d31c61189cc92415). The [versioned release record](RELEASE-1.1.0.md) links npm artifact integrity, attestation, release workflow and the official Registry entry. The imported monorepo commit `683b3ac9294e9db795607470dc632c13f79d68b8` is a separate source identity. It is not the build commit or the identity of the historical 1.0.2 package.

[SOURCE.json](SOURCE.json) is the frozen import-time inventory: imported commit, release tag and SHA-256 hashes of the complete MCP and shared core source, registry manifest, license and changelog. Its `publicationStatus` and the imported changelog retain their preparation-time wording. They describe the source at import, not the subsequent publication state. Hashes normalize CRLF to LF so Windows and Linux verify the same text.

The original server and shared core import comes from that exact commit. Immutable monorepo commit `cb4bbddb432716d02a0cfb4224823810f0fb8c3e` supplied the explanation side-effect and minimized duplicate-input contracts, and `3ab8815c4d695947a116d227cd487142e2efc604` supplied the dedicated widget origin and bounded density recovery. The latest update imports seven MCP and shared-core runtime files from immutable monorepo commit `7651c22dfc77d499e6587ae971399a017be2441e`. `SOURCE.json.sourceUpdates` retains the earlier updates and records this superseding per-file identity. A reviewed follow-up imports only `packages/core/src/index.ts` and `src/apps.generated.ts` from immutable monorepo commit `51e43cb1fa92e606ff590cfb323e3759df68bf7e`. Those two current files match the follow-up commit. The final factual description update imports only `src/tools.ts` and `src/docs.generated.ts` from immutable monorepo commit `34c9cb98c858174dd44bece40df6a3766722583a`. The remaining three variant exports match `7651c22dfc77d499e6587ae971399a017be2441e`, and all other inventory entries retain their prior identity.

The latest shared helper creates six-part heatmap keys that include the selected variant. Factual tool descriptions and schemas distinguish `variantScope: single` from historical five-part `variantScope: pooled`; reporting guidance remains in server instructions. The generated viewers visibly show Variant: control (or the selected value), No variant recorded for an empty value, or Historical pooled variants beneath the route. Long variant identifiers wrap within narrow metadata. The shared comparison helper uses exact raw variant and resolved scope, so empty values cannot alias literal label text. Historical pooled cells are retained without an invented per-variant split. The API intake, findings folding and historical continuation/retraction repair lives in the monorepo and is not exported as an API implementation here. This mirror exposes that API contract and renders its metadata; it does not migrate customer data or claim deployed grouping behavior from source alone.

The existing `ui.domain` remains `https://mcp.hootlens.com`. The explicit Load click density action still requests at most 200 cells for the same project and cohort through the authorized host; `maxCells: 0`, loading, refusal/retry and stale-response safeguards remain. Explanation side effects and minimized duplicate-check inputs remain as previously reviewed. The final variant source update did not change scopes, CSP, dependencies, version or registry metadata.

Shared core source and generated MCP resources are included so no private repository access is required to build. No API implementation, server credentials, environment file or customer data is exported. The public build script adapts the two-bundle builder to this repository. The root manifest stays `private: true`; dependencies, source inventory and compiled version are checked before staging the strict npm payload.

Version 1.1.0 was subsequently published on 14 October 2026. Its import inventory deliberately remains unchanged, with no retroactive npm integrity or attestation fields. The [release record](RELEASE-1.1.0.md) records those publication facts separately. Source hashes and successful fixture tests are not npm provenance or a binary reproducibility claim. Historical published 1.0.2 source and security evidence remain available in Git history and the versioned security evidence documents.

## Synchronize an already published source snapshot

These steps describe historical exports of versions published from the monorepo. New releases through public CI use [RELEASING.md](RELEASING.md) instead. Their npm `gitHead` and attestation identify the public build commit; the imported monorepo commit remains a separate source reference. Do not claim the two commit identities or independently built bundle bytes are identical.

1. Fetch the exact release tag from the owner's monorepo. Compare its commit with `npm view @hootlens/mcp@VERSION gitHead dist.integrity --json`. Do not export a development branch under a published version.
2. Copy `services/mcp/src`, the shared `packages/core` source required by it, `server.json`, `LICENSE` and `CHANGELOG.md`. Review the complete file set for secrets and customer data. Preserve the source mirror's build, test and CI files.
3. Update the root manifest and dependency lock from that release, keeping this mirror private. Adapt build paths and include any new shared runtime dependencies. Regenerate the normalized hashes and release identity in `SOURCE.json` from the tagged source, rather than hashing an unverified working tree.
4. Run `npm ci`, `npm run typecheck`, `npm run build`, `npm test`, and check the built executable's version. Review the actual public CI matrix, the installed npm artifact and the hosted endpoint separately.
5. Open a public repository PR. Merge after independent review and passing required checks. Synchronize official registry metadata with the already published npm version, using the owner's existing domain proof. Historical exports do not authorize republishing an existing npm version. For future public releases, follow the separate [release procedure](RELEASING.md).

Neither a local fixture test nor a matching version proves production authorization, customer capture, signed-in client compatibility or directory acceptance. Keep those checks in their own evidence records.
